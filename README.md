# 知到自动助手

智慧树 / 知到平台（`zhihuishu.com`）的 Chrome 扩展。四个核心能力：

1. **自动连播** —— 视频播完自动点目录里的下一节，跳过已完成和未解锁的节点，
   支持两层/三层的嵌套目录（`1.2 → 1.2.1 / 1.2.2 / 1.2.3`）与自动展开折叠章节。
2. **自动作答** —— 两种场景二选一（视频课中弹题 / 能力提升整页卷子），两级降级求解：**问网页版免费 AI → 题库命中**。两级都不中就停下来交给你手动答（组合枚举默认关闭，见第三节）。
3. **网页版 AI 抢答** —— 把题目丢给已经登录的豆包 / DeepSeek / Kimi / 通义千问 / 腾讯元宝，
   把答案扣回来直接作答；等不到答案就自动落回下一级，不会卡住整节课。
4. **反检测** —— 用 CDP 派发真实点击与真实输入，绕开平台对 `isTrusted` 的判定，
   避免被识别成"异常脚本"后暂停播放、踢回首页。

已在真实 Chrome 里跑通完整链路：接管播放器 → 自动答对弹题 → 播完 → 自动切下一集 → 继续答对 → 目录打钩。
同时有 361 项自动化测试覆盖核心逻辑、网页 AI 链路、目录识别、弹题探测、提交环节、控制台接线与端到端流程。

## 一、安装

1. 打开 `chrome://extensions`
2. 打开右上角的**开发者模式**
3. 点**加载已解压的扩展程序**，选中本目录 `zhihuishu-auto`
   （必须是含 `manifest.json` 的这一层，不要选它的上级目录）

安装时 Chrome 会提示这个扩展会"调试浏览器" —— 这是反检测功能必需的 `debugger` 权限，原因见第四节。

它同时会申请几个 AI 站点的访问权限（豆包 / DeepSeek / Kimi / 通义 / 元宝）——
那是「网页 AI 抢答」要在那些页面上问问题用的。不用这个功能的话，
把控制台里的开关关掉即可，不会再去碰这些站点。

4. 加载后卡片上不应有任何红色「错误」

> 改了任何代码后，**必须回 `chrome://extensions` 点扩展卡片上的刷新按钮**，
> 光刷新页面没用。也可以点工具栏图标打开控制台，用里面的「重载扩展」按钮。

装好后打开任意知到课程页，扩展会自动接管；工具栏图标上会实时显示当前播放进度百分比。

## 二、快速验证（不用登录知到）

仓库自带一个离线模拟页，可以在不碰真实课程的情况下确认扩展工作正常：

```bash
node tools/serve.js          # 默认监听 127.0.0.1:8899
```

然后浏览器打开 `http://127.0.0.1:8899/`。

模拟页把 `<video>` 的状态做了可编程化处理（改写 `duration` / `paused` / `currentTime` 的 getter），
所以不需要任何真实视频文件，也不需要网络。五节课，每节 20~32 秒，每节课中途必弹两道题，
题的正确答案每次刷新随机。

页面底部状态栏有三项关键指标：

| 指标 | 含义 |
| --- | --- |
| **接管** | 「已接管」= 扩展成功注入并控制了播放器 |
| **反检测** | `未检出合成事件 · click N` = 扩展的所有点击都没被识破 |
| **弹题** | 「已答对」= 弹题被自动解掉了 |

判断扩展端到端工作正常的标准：**左侧目录第一行末尾出现绿色 ✔，并且播放自动跳到了第二行。**
出现 ✔ 意味着「播放 → 弹题 → 自动答对 → 播完 → 切集」这条链全部走通了。

「反检测」那一项里的 **click N** 是页面收到的点击总数（含你自己手点的），
**未检出合成事件**才是关键 —— 它说明扩展的自动点击全部通过了 `isTrusted` 检查。
一旦变成「检出合成事件 N 次」，说明 CDP 那条通道断了。

## 三、自动答题是怎么工作的

知到有**两套完全不同的答题场景**，页面结构和操作方式都不一样，所以是一个**单选模式**：

| 模式 | 场景 | 怎么工作 |
| --- | --- | --- |
| **视频**（默认） | 视频课：看着看着弹一道题（浮层） | 答完关掉继续播，一题一次独立问询 |
| **能力提升** | 一整套卷子铺满整页 | 一题一题翻、逐题作答，最后统一提交 |

> ### 两者**必须互斥**（这是硬要求）
>
> 它们**共用同一个网页端 AI 标签页**。同时问会互相踩：一处刚把题目打进输入框，
> 另一处把输入框清了 —— 两边都拿不到答案，还会把对话污染掉。
>
> 隔离靠三道闸门，任何一道单独成立都不会出问题：
>
> | 闸门 | 位置 | 作用 |
> | --- | --- | --- |
> | 配置**单选** | `defaults.js` 的 `mode` | 只有一个值，从配置层堵死"两个都开" |
> | 启动闸门 | `main.js` 的 `tick()` | 只有当前模式那套会被启动，另一套直接不进来 |
> | AI 通道**排队** | `ai-bridge.js` + `service-worker.js` | 即使两边都被触发，后来的**等**前面的走完 |
>
> 第三道是关键：以前 background 是"忙了就拒绝"（返回「AI 正在回答上一道题」），
> 上层拿到这个就落到题库/枚举 —— 从外面看完全是"随机失败"。
> 现在是**排队**（上限 90 秒），"不同时使用同一个 AI 页"靠排队实现，不靠调用方自觉。

**默认顺序是「网页 AI → 题库」**，两级都不中就**停下来交给你手动答**：

```
网页 AI ✓ → 成功
        ✗ ↓
题库    ✓ → 成功
        ✗ ↓
        放弃本题（不自动交答案）
```

> ### 为什么默认不再枚举
>
> 组合枚举 = 把同一道题**反复提交**（多选最坏二十几次）。
> 而这一版默认走网页 AI，智能体的网页端对**重复提问**很敏感 ——
> 同一道题在原对话里再问一次，它要么不答、要么回一句「这个问题我已经回答过了」。
> 于是枚举就和"AI 答错一次"撞在一起：AI 给错答案被判错 → 平台回退重播 →
> 同一题再弹 → 再问 AI（它拒答）→ 再枚举 —— 来回空转，还反复把视频拖回去。
>
> 与其空转，不如**停手**：哪道题没答上，日志里会明确写出来，你手动点一下就好。
> 想恢复硬试，控制台里有「组合枚举」开关，打开即恢复旧行为（算法没删）。

可在控制台把 AI 挪到题库后面（已做过的题零等待秒过）。

### 1. 网页版 AI（默认打头）

拿到弹题就把题目交给**已经登录的免费 AI 网页版**问一次答案：

| 站点 | 说明 |
| --- | --- |
| Gemini | `gemini.google.com/app`（含各地区镜像 `.co.jp` / `.com.hk` …）|
| DeepSeek | `chat.deepseek.com` |
| 豆包 | `www.doubao.com/chat/` |
| Kimi | `www.kimi.com` |
| 通义千问 | `www.tongyi.com/qianwen/` |
| 腾讯元宝 | `yuanbao.tencent.com/chat/` |

> **Chrome 右上角那个「询问 Gemini」不是这个。** 那是浏览器自带的侧边栏，
> 它不在任何网页里，扩展的 content script 注入不进去 —— 谁也没法去点它。
> 要用 Gemini 的话，把 `gemini.google.com` 开成一个普通标签页就行，
> 扩展会复用/新开它，跟别的站点一模一样。

> ### ⚠ 前提：需要把浏览器挂在 AI 页面
>
> **只有当浏览器主页面（当前激活的那个标签页）是 AI 端时，上面这些针对
> AI 答题的改动才能正常运行。**
>
> 具体说：**AI 站点那个标签页必须是前台激活的那一个**，知到页放在后台待着。
> 反过来的话（看着知到页、AI 页被切到后台），这一级会出现各种
> "题目进不去"、"字进去了发不出去"、"点了没反应"的失败 ——
> 而且现象看起来像是插件坏了，其实只是标签页没在前台。
>
> 原因：这一级靠 CDP 往 AI 标签页里派发键鼠事件，而回车/点击这类操作
> 依赖页面自身的焦点状态。标签页不在前台时，焦点和可见性都会变，
> 站点自己的发送逻辑就不认这些事件了。
>
> **所以排障顺序里，第一件事永远是先确认 AI 页在前台。** 「试发一条」
> 报回来的失败现场，如果不是这个前提，基本都不用往下看。

控制台里可以指定用哪一家，默认「自动」——哪个开着用哪个。链路是这样的：

```
知到页  QuizSolver.solveViaWebAI()
   ↓ ZHS_AI_ASK（题干 + 选项 + 题型）
后台     找有没有开着的 AI 标签页；没有就后台新开一个（active:false，不抢焦点）
   ↓ chrome.tabs.sendMessage
AI 页    找输入框 → CDP 塞字（Input.insertText）→ 点发送 → 等流式输出停 → 解析
   ↓ 字母 A/B/C… → 下标
知到页   按 AI 给的下标勾选 → 提交 → 走同一套判定
```

> **AI 优先 ≠ 每次都问。** 后台有应答缓存，同一道题第二次弹出来是直接命中缓存的，
> 不会真的再去骚扰一次 AI 站点。再加上"上一轮 AI 给的组合已经试过就不再问"这层
> 会话记忆，实际问询次数远少于弹题次数。
>
> 想反过来省时间就关掉控制台里的「AI 优先」：那样已做过的题会先走题库秒过，
> 只有没见过的题才去问 AI。

几条是踩过亏的设计，别随手改：

- **提示词短到极致，而且绝不给出任何具体答案字母**。这几条都是踩过亏才定下来的：

  1. **末尾不能写具体示例**。以前是 `答案：B（只写字母）` —— 结果模型不看题、
     直接抄那个 `B`，表现就是"答案永远等于示例里那个字母"。
     现在写的是格式占位：`最后只回一行：答案：<单个字母>`。
  2. 早先的版本还带【题型】【输出格式】【规则 1/2/3】和「理由：不超过 20 字」（480 字 13 行），
     实测在豆包 / DeepSeek 上**发不出去** —— 空行、`【】` 和"不要…不要…"的多行清单
     会让发送按钮一直不点亮。现在一个四选项的题只发 7 行、两百多字：

  ```
  直接说出答案，不用解析。
  题目：以下哪个是 HTTP 协议的默认端口？
  A. 21
  B. 80
  C. 443
  D. 8080
  最后只回一行：答案：<单个字母>
  ```

  第一行那句是**必须的**：不给它，模型会先写一整段分析再给结论 ——
  长推理既拖慢等待，也更容易在中途跑偏。末行的 `<单个字母>` 只传达"要用这个前缀"，
  不给任何字母当锚点（`buildPrompt(quiz, { showExample: false })` 可以整行去掉）。
- **塞字有三条路径，而且优先走「不需要焦点」的那条**。
  以前默认走 CDP 的 `Input.insertText` —— 它是往**当前焦点**里写，而焦点恰恰是最容易被
  抢走的东西（点了发送按钮、页面自己重渲染、被别的扩展的遮挡层接走点击）。
  现在顺序是：
  1. DOM 原生 setter（textarea）/ `textContent` + `input` 事件（contenteditable）—— **不需要焦点**
  2. CDP `insertText` —— 只在焦点确实在输入框上时才试
  3. `execCommand('insertText')` —— 给 contenteditable 站点的兼容兜底

  每一条之后都用「塞进去多少字」复核，不认"我调过 API 了"。
  ⚠ 这里有个真 bug 的教训：`el instanceof HTMLTextAreaElement` 里那个构造函数
  **不保证存在于当前作用域**（扩展重载后的旧世界、各种沙箱里都是 undefined），
  它一抛 `ReferenceError`，整个 try 连同后面的兜底路径一起完蛋 ——
  表现就是"字永远塞不进去"。现在改成安全的原型链查找。
- **已打开的 AI 标签页上没挂脚本时，后台会按需补注入一次**。
  manifest 的 `content_scripts` 只在页面加载时注入一次 —— 扩展装好之前就开着的页、
  扩展重载过而页面没刷新的页，里面都是没有我们的脚本的。
  以前这种情况会报一句很误导人的「AI 页无响应（可能没登录或被卸载）」，
  现在先补注入、再 ping、实在不行才报错，并且报错会直接让你刷新那一页。
  （所以 `src/ai/web-ai.js` 里也带了防重复注入的守卫：手动补注入时不会把监听器叠两遍。）
- **发送是循环重试的，而且有独立时限**：**等发送按钮变成"能按"** → 点它 →
  重新聚焦输入框 → 敲原生回车 → 换纯键盘序列（`rawKeyDown` + `insertText('\r')` + `keyUp`）
  → **回到第一步**，直到确认发出去或 `sendDeadline` 用完（`min(总等待 - 4s, 12s)`）。
  「试一遍就放弃」是不行的：那种表现就是弹窗一直挂着、视频一直被 hold，
  看着就是插件卡死。但也不能无限试下去 —— 给"发"这一步单独设了上限，
  给后面等回包留出渲染余量。
- **发送按钮要"挑"出来，不是"谁先命中就点谁"**。
  这一条是「字打进去了但发不出去」真正的根因。DeepSeek 的输入框旁边，
  「深度思考」「智能搜索」两个**模式开关**也是 `div[role="button"]` ——
  和发送箭头长得一样"合法"。而站点表里恰好有一条泛化选择器：

  ```
  send: [
    'div[role="button"][aria-disabled="false"]._7436101',   // 旧哈希，多半失配
    'div[role="button"][aria-disabled="false"]',            // ← 泛化，命中了模式开关
    'button[aria-label="Send message"]',                    // ← 真正的发送键，却排在后面
  ]
  ```

  旧代码 `findSend = anyVisible(...)` 是"第一个可见的就点"，
  于是点的是模式开关：界面毫无变化，字仍在输入框里，重试多少轮都一样。

  现在改成**给候选打分排序**，判据从硬到软：`aria-label` 带 send/发送/提交 →
  class 带 send/submit 或 `type="submit"` → 文本就是"发送" → 和输入框在同一个容器里 →
  是真 `<button>` → 当下"能按"。同时把明显不是发送键的（模式开关、附件、语音、
  菜单、停止生成……）**重罚出局**。并且每轮换下一个候选 ——
  万一排序还是猜错了，下一轮会自动改试另一个，而不是忠实地反复点同一个没用的东西。
- **点发送按钮之前要先等它变"能按"**，而**等不到也要照点**。
  站点把我们的字收进自己的状态之前按钮是禁用的，这时候点它等于什么都没发生 ——
  而字已经进去了，从外面看就是"第一次只把题目打进了输入框、没有发送"。所以：
  - 先等（最多 1.2 秒）它变成能按的样子；
  - 等不到（有些站点压根不给禁用态）就**照点**；
  - 点完**不急着下结论**，紧接着在同一轮里补回车 —— 点它和敲回车本来就是
    同一个动作的两种表达，连着做比分开试成功率高得多。

  ⚠ 中间修过一次自己的回归：最初的写法是 `if (btn && ready)`，
  **等不到就不点**。而"禁用"的判据（`aria-disabled` / `disabled` / 半透明）
  不一定挂在真正能点的那个元素上（可能挂在外层容器），真按钮的透明度
  也可能刚好在过渡动画中途。判据一误伤，唯一有效的那一路就被自己关掉了。
  **等是优化，拒绝点击是事故** —— 点击本身只要几毫秒。
- **每次提问都从"干净的输入框"开始** —— 这一条对应「二次提问发不出去」。
  第一次提问之所以正常，就是因为那时输入框是空的。而上一问如果**没被判成
  "发出去了"**，重试循环会把同一段文字重新塞回输入框；下一问开始时就变成
  "旧题 + 新题"连在一起发出去：

  ```
  直接说出答案，不用解析。
  题目：上一道题？          ← 上一问的残渣
  ...
  答案：B直接说出答案，不用解析。   ← 和下一问粘在一起
  题目：这一道新题？
  ```

  所以开问之前先 `clearComposer`（DOM 路径优先，被受控组件拒绝就退回
  "全选 + 删除"）。**每一次提问都走和第一次完全相同的路径**，
  不去为"第二问"特判什么。
- **选项要点"可点部位"，不是整行的几何中心**。
  这一条对应「插件没法自动选择选项」。知到的选项是**满宽的一行**：
  `<li class="subject_node_item">` 里面是 `<span class="tag">A</span><span>对</span>`，
  单选框在**最左边**。而点击走的是元素的几何中心 —— 落点在右边一大片空白上，
  点下去什么都不会发生。行看着能点（选中时整行会变色），但"能点"和"点中心"是两件事。

  所以按优先级找一个更小的目标：
  `input`/`label` → 圆圈类元素（radio / check / circle / tag / icon）
  → 行内第一段有文字的末梢节点 → 兜底整行。

  而且点完**要确认真的动过**：比对这个元素"点之前 / 点之后"的指纹
  （class + style + aria + 内层长度）。没变就说明内层不是可点部位，
  再补一下整行 —— 两种挂法（挂内层 / 挂整行）都覆盖到，且不依赖任何 class 名。

  等待用**轮询**而不是固定 sleep：选中态通常是同步加的 class，40ms 就能观察到；
  固定等 200ms 不光白等，还会把整套枚举的时间拖长（e2e 就是这么被拖垮过一次）。
- **按钮文案按语义认，不按清单认**。提交按钮曾经是一张**精确匹配的清单**
  （`/^(提交|确定|确认|保存|下一题|…)$/`），而站点上摆的是**「提交作答」** ——
  一条都不命中，于是日志报「没找到提交按钮（可能是"点选即提交"的题型）」，
  而按钮明明就在眼前（蓝色，写着"提交作答"）。
  清单永远列不全站点的写法，所以改成**短文本 + 含提交类动词**：
  提交 / 提交作答 / 提交答案 / 确认提交 / 立即作答 / 开始作答 / 交卷 / 确定 / 完成
  都能认。"短"这个上限不能省 —— 弹窗正文里也可能含"提交"两个字，
  不限长度就会点到一段说明文字上。翻页按钮（上一题 / 下一题）同理。
- **连续提问时，要先把上一轮的生成停掉**。
  这一条对应「连续提交时后面的提交不上」：第一问完全正常，第二问的字进了输入框
  却发不出去 —— 因为上一轮的回答还在流式输出时，composer 上那个按钮是
  **「停止生成」**而不是「发送」：点它只会把上一条回答掐掉，回车也不发消息。
  以前这里只是"等 3 秒"就往下走，而模型还在写，等于白等一轮又一轮。

  现在**主动点掉停止键**，让 composer 回到可发送状态再开始这一问
  （上一条的答案我们已经读完了，停掉它是安全的）。判据分宽严两套：
  - 宽判据（`div[class*="stop"]`）只用来"等" —— 它可能命中一个跟停止无关的元素；
  - 严判据（必须明确写着"停止 / Stop"）才敢真的点下去。

  另外第一轮的"等发送按钮变能按"给到 2.5 秒（页面刚起来、字刚进去，
  按钮点亮得慢），后面几轮缩到 1.2 秒。
- **答不出来时，先看看"读"的那一步断没断**。站点改版最常打掉的不是发送，
  而是**读回答**：选择器匹配不到回答元素，于是"问题已经发出去了、AI 也答了"，
  插件却说失败。所以读回答有两级：
  1. 按站点表的选择器找（正常路径）
  2. **结构兜底** —— 从输入框往上找到"对话那一列"，取那一列里
     **最后一块有文字的末梢节点**。最新的回答必然是它。

  第 2 级是必需的：DeepSeek 的回答经常就是干干净净一行 `答案：B`，
  **没有** `.markdown` 之类的容器（那些 class 只在回答里带格式时才出现），
  只靠选择器会一条都匹配不到。
- **选项自带的前缀要剥干净，包括"裸空格"那一种**。知到渲染出来的选项文字是
  `A 西方意象派…`（字母 + 一个空格，没有任何分隔符），旧的正则只认 `A.` / `A、` / `A)`，
  于是发出去的提示词里出现两套字母：
  ```
  A. A 西方意象派诗歌完全模仿中国古典诗歌的形式      ← 用户看到的就是这个
  ```
  模型对着双字母选项容易被带偏。现在 `A.` `A、` `A 对` `（A）` `A·` 都剥，
  但"整个选项就叫 A"这种不会被剥成空串。
- **判"发出去了没有"不看消息条数**，看三个信号：
  输入框被清空 / 回答区指纹动过 / 题目前 12 个字出现在页面上。
  指纹 = 「最后一条回答的元素引用 + 它的文字长度」。
  为什么不用条数：站点的回答是**流式渲染**的，同一屏里"最内层"元素的数量
  会在渲染过程中忽增忽减（先出现外层容器、再长出内层 markdown），
  于是"条数涨了吗"会时灵时不灵。
  另外 `isVisible()` **刻意不要求元素落在视口内** —— 以前多要求了
  `r.bottom > 0 && r.top < vh`，结果聊得久一点、回答被滚出视野之后那些消息
  就被判成"不存在"，表现正是"问题明明发出去了，插件却说没发出去"。
- **只认「答案：X」那一行**，定位和取字母是**两步**分开做的：
  先用正则找到「答案 / Answer」标记的位置，再从那里往后**扫描**字母。
  合成一条大正则试过三次都失败 —— `答案：A、C` 这种多选上，惰性量词会满足于
  `答案：A、` 就收工（`、` 属于"非字母"，收尾条件提前成立），换前瞻、换锚、
  放宽字符类都只是把问题挪个地方。扫描器还顺手解决了这些：
  `【答案】D`、`（答案）B`、`Answer: D`、全角 `Ｂ`、
  `答案：B。因为 B 更合适`（解释里的 B 不会被当成答案）。
  提示词里那行格式占位（`答案：<单个字母>`）被原样抄回来时判为"没给答案"。
  没有这一行才退化：判断题认句尾的「正确 / 错误」，短回包（≤12 字）认「B」「选 B」这种。
  散文里散落的字母一律不猜 —— 题号、选项名、`TCP` / `OS` 这些缩写到处都是字母，
  猜错一次要等平台判错、回退重播，代价比多枚举一轮大得多。
- **只试一次 AI 给的答案**。AI 不可能是"半对"，答错说明它压根不会这道题；
  而且那一次错误提交会被记进「已试过」，枚举不会把同一个错答案再交一遍。
- **超时是硬上限**（默认 90 秒，可在控制台 15s~180s 调）。等待期间弹窗还开着、
  视频还被 hold 着，到点必须返回并落回下一级 —— 这条链路只负责"更快"，
  不能变成"必须成功否则答不了题"。
  默认给到 90 秒是有意的：免费的 DeepSeek 想复杂一点的题经常要 40~70 秒，
  而"等得久"和"等不到"是两种代价 —— 等得久只是慢，等不到就得交回给你手动答。
  等待期间每 5 秒往日志里报一次进度，控制台那一格也会显示「等待 42/90s」，
  免得一声不吭地干等被当成卡死。
- **答对的答案照旧记进题库**，所以同一道题第二次出现是零成本，连 AI 都不用问。

代价说清楚：需要一个已登录的 AI 网页版；首次触发会多等十几秒（模型在写）；
配额用尽或被限流时它会失败，然后自动落回下一级。

### 2. 题库命中

题干经过归一化（全角转半角、去空白、剥离题号前缀）后取哈希，
连同「选项数量 + 单选/多选」一起作为题目身份键。

```
"1、下列哪个选项是正确的？"  ┐
"下列哪个选项是正确的?"      ├─→ 同一个键
"下列哪个选项是正确的。"     ┘
```

命中就直接按记录的答案作答 —— 零等待。选项数量变了、或记录的下标越界，
就判定为失效并丢弃该记录，继续往下走。AI 那边答对的题同样会写进这个题库。

### 3. 组合枚举（默认关闭）

> 这一级**默认是关的**，理由见上一节。把它打开之后的行为如下。

前两级都没给出答案时，按**组合长度升序**枚举选项子集：

| 题型 | 枚举顺序 |
| --- | --- |
| 单选 / 判断 | `[A]` `[B]` `[C]` `[D]` |
| 多选（4 选项，上限 3） | 先试 1 个 → 再试 2 个 → 再试 3 个 → **最后补一次全选** |

每种组合的动作是：**清空当前选择 → 勾选 → 复核选中态 → 提交 → 等待判定 → 失败就换下一个**。

「复核选中态」这一步是必需的：平台在答错之后会把选择重置掉，这个重置的时机不受我们控制，
有可能正好落在「勾完最后一个选项」与「点提交」之间 —— 那样提交出去的是一次空选择，
判定必然失败，枚举再多次也命中不了正确答案。所以勾完要验一遍。

但**"验"本身有个必须承认的边界**：知到不同题型的选中态画法不一样
（有的加 class、有的改内层圆点的样式、有的用行内 style）。判据一条都不命中时，
我们**并不知道**是"真的没选中"还是"我们看不出来"。把这两件事当成一件，
就会陷入日志里那种空转：

```
勾选 A → A
选项在提交前被平台重置，补点一轮
选项在提交前被平台重置，补点一轮     ← 同一件事重复报，最后还是判定超时
```

而且"补点"那一路会先 `clearSelection` —— 判据一旦是瞎的，
清掉的正是刚选上的东西。

所以选中态是**三态**：

| 返回 | 含义 | 动作 |
| --- | --- | --- |
| `true` | 明确选中了 | 提交 |
| `false` | 明确没选中（`inactive` / `unselected` / 内层 radio 没勾） | 补点一轮 |
| `null` | **看不出来** | 相信刚才那一下点击，照常提交，并把标记打进日志 |

`null` 那一路还会把选项的 `class` / `style` / 内层 HTML 打出来 ——
下次拿到真的标记名，就能把判据补准，而不是继续猜。

另外判定超时且**没有任何信号**时，会再补一次提交
（很可能是按钮被禁用、或者点击没落到按钮上），而不是直接把这道题当成答错。

枚举序列的**末尾会补一个全选**组合。多选里「以下哪些属于…」的正确答案常常就是全部选项，
如果上限把它挡在外面（默认上限 3 < 4 个选项），枚举跑完也解不出来。

### 4. 判定

判定不靠单一信号，而是多路投票，避免被题干里的「正确」二字骗到：

| 信号 | 结论 |
| --- | --- |
| 弹窗从 DOM 消失或不可见 | 通过 |
| 题干被替换成下一题 | 通过 |
| 页面上新出现「回答正确 / 答对了 / 太棒了」等短提示 | 通过 |
| 弹窗内新出现「回答错误 / 不正确 / 再想想」等短提示 | 失败 |
| 都不出现，等到超时 | 继续试下一个组合 |

关键细节：**不看「视频是否恢复播放」**。平台的自动恢复、以及本扩展自己的保活逻辑都会让视频在答错后照样跑，
拿它当判据会把每一次答错都误判成答对，枚举就永远停在第一个组合上。

### 5. 防重复

答错之后平台常常会**回退视频重播同一道题**。已试过的组合记在会话记忆里，
题目再次弹出时直接跳过，不会从头再来一遍。

答对之后弹窗往往要停一两秒展示「回答正确」才关闭，这期间主循环还会再次检测到同一道题。
这里用弹窗 **DOM 节点身份**做了拦截：节点没换就说明还是同一个弹窗，直接放行不再重复提交；
节点换了才当作新题处理。

## 四、反检测

### 平台在查什么

从学习页主包（`wisdom-mooc.zhihuishu.com/assets/index-*.js`）里能读到两处判定：

**① 合成事件的 `isTrusted`**

```js
document.getElementById('container').addEventListener('click', e => {
  e.preventDefault();
  e instanceof Event && (e.isTrusted || ve(window.XMLHttpRequest));
}, true);                                   // ← 捕获阶段，业务代码干扰不了

// 进度上报函数也会检查末位参数
function gn(...) {
  if ([...arguments].pop() instanceof PointerEvent && arg.isTrusted === false) { ve(); return; }
  ...
}

function ve(ce) {
  le.value = { icon: 'warn', msg: s('argsMsg02') };   // 「检测到异常脚本…」
  _(ce);
  window.ablePlayerX('container').pause();
  setTimeout(() => location.replace('https://www.zhihuishu.com'), 3000);
}
```

**② 播放速率**

```js
onTime: fe => {
  document.querySelector('#container video')?.playbackRate > 1.8
    && (pause(), alert(s('elMsg01')), location.replace('https://www.zhihuishu.com'))
}
```

### 为什么不能在 JS 里伪造 isTrusted

最直觉的做法是替换 `Event.prototype.isTrusted` 的 getter。**这条路走不通**。实测（Chrome 154）：

```
Object.getOwnPropertyDescriptor(Event.prototype, 'isTrusted')  → undefined
Object.getOwnPropertyDescriptor(new Event('x'), 'isTrusted')   → { get: ƒ, configurable: false }
```

`isTrusted` 挂在**每个事件实例自己**身上，而且是 `configurable: false` —— 原型上没有它，
实例上又改不动。任何"主世界替换 getter"的补丁都是打在空气上，看起来做了防护，实际一点用没有。

（这个结论在真实浏览器里验证过，测试里也留了一条断言守着它，防止有人又回去写原型补丁。）

### 实际采用的手段：CDP 派发点击

既然伪造不了，那就让点击**在浏览器层面就是真的**。

扩展通过 `chrome.debugger` 附加到标签页，用 CDP 的 `Input.dispatchMouseEvent` 派发鼠标事件 ——
这样产生的事件 `isTrusted` 天生为 `true`，页面那两处判定都会正常通过。

```
content script  realClick()
      ↓ 算出元素中心相对顶层视口的坐标（累加各层 iframe 偏移）
      ↓ chrome.runtime.sendMessage({ type: 'ZHS_CDP_CLICK', x, y })
background      chrome.debugger.sendCommand('Input.dispatchMouseEvent',
                  mouseMoved → mousePressed → mouseReleased)
```

派发的是完整的 `mouseMoved → mousePressed → mouseReleased` 序列，和真人操作产生的事件流一致。

代价（这是要权衡的）：

- 浏览器顶部会常驻一条「XX 正在调试此浏览器」提示条
- 附加期间打不开 DevTools
- 同一时刻只服务一个标签页

控制台里有一个「高保真点击」开关可以关掉它。**但关掉之后所有点击都带着 `isTrusted=false` 出去，
平台的检测会立刻命中** —— 只有在平台改了检测方式、或者你只是想在本地跑测试时才应该关。

### 倍速

`1.8` 是平台写死的判定线，不是经验值。所以：

- popup 滑块最大只到 1.8
- 配置读取、写入、下发的每条路径都会 clamp，历史配置里存的越界值也会被收回来
- 外部直接改 `video.playbackRate` 会被守卫压回去

### 自己验证

模拟页底部状态栏的「反检测」和「诊断」两行：

- `未检出合成事件 · click N` —— 扩展的所有点击都没被识破
- 诊断行会显示 `isTrusted` 的实际挂载位置，解释为什么必须走 CDP

在这个页面上关掉「高保真点击」再刷新，你会看到它立刻变成「检出合成事件」，
而真实知到页面上的结果就是那条「检测到异常脚本」的提示。

默认 **1.0×**，上限锁死 **1.8×**（原因见上一节 ②）。

另外知到还会校验「有效学习时长」与视频时长的对应关系，倍速拉高容易出现进度走完但学时没记上的情况。

### 网页 AI 抢答

| 项 | 默认 | 说明 |
| --- | --- | --- |
| 用网页版 AI 答题 | 开 | 关掉就只剩题库一级（枚举默认关着，等于只答题库里有记录的题） |
| **AI 优先** | **开** | 开 = 顺序为 **AI → 题库 → 枚举**；关 = 题库优先，做过的题秒过、没见过的才问 AI |
| 站点 | 自动 | 自动 / Gemini / DeepSeek / 豆包 / Kimi / 通义千问 / 腾讯元宝 |
| 应答等待 | **90s** | 等 AI 回包的上限（15s ~ 180s）。超时自动落回下一级，不会卡住整节课 |

> **这个预算是怎么切的。** 「应答等待」不是"只给模型思考"的时间，而是
> **从进到 AI 页面那一刻起的整个预算**，在里面切成两段：
>
> | 应答等待 | 发送段 | 留给读回答 |
> | --- | --- | --- |
> | 15s | 10s | 5s |
> | 30s | 15s | 15s |
> | 60s | 30s | 30s |
> | 120s | 60s | 60s |
>
> 发送段 = 预算的一半（下限 10s、上限 60s），并且永远给"读"留至少 30%。
> **两段一起随预算变**。
>
> ⚠ 这里踩过坑：早期的写法把发送段上限**写死成 15 秒**。后果是用户把
> 「应答等待」调到 60s 甚至 180s，发送阶段仍然只试 15 秒就放弃、报
> 「问题没发出去」—— 从用户角度看就是"我明明调长了，它还是那么快就失败"。
> 失败报告里现在会写明实际用了多久、上限多少，一眼能分清
> "时间用完了"和"被提前掐掉了"。
| 没打开就自动新开一个 AI 标签页 | 开 | 新开的标签页在后台（不抢焦点）；关掉则只复用你已开的 |
| 同一道题复用上次问到的答案 | 开 | 命中缓存时**零等待**，不再去骚扰 AI 站点 |

> **Chrome 右上角那个「询问 Gemini」不是这个。** 那是浏览器自带的侧边栏，
> 它不在任何网页里，扩展注入不进去 —— 谁也没法去点它。
> 要用 Gemini 就把 `gemini.google.com` 开成一个普通标签页，扩展会复用/新开它。

> 这些站点都要**先登录**。扩展不会替你去登录，也不会碰你的账号 ——
> 它只是在你已经打开的页面里，替你打一行字、读一行答案。

改默认值：`src/shared/defaults.js`。历史配置存在 `chrome.storage.local.config` 里，
新加的键在读取时会用默认值补齐，不需要手动迁移。

### 动作

| 按钮 | 用途 |
| --- | --- |
| 立即答题 / 切下一集 / 重扫目录 / 探测弹题 | 手动触发，排障用 |

| 导出题库 / 清空题库 | 题库是 JSON，可以备份和共享 |
| 清空 AI 缓存 | 清掉「问过的题 → 答案」，下次会重新问 |

## 七、故障排查

### 弹出「检测到异常脚本」

平台的两处判定（见第四节）之一被触发了。按顺序排查：

1. **DevTools 是不是开着？** 这是最常见的坑 —— `chrome.debugger.attach()` 在标签页已被
   开发者工具占用时会直接失败（`Another debugger is already attached to the tab`），
   扩展会自动退回合成事件，而合成事件的 `isTrusted` 是 false，平台立刻命中。
   **按 F12 关掉开发者工具**，刷新页面即可。
   想知道到底有没有失败，看 Console 里有没有
   `CDP 点击失败，已退回合成事件（会被平台识破）：<原因>` 这一行 —— 有它就是这条。
2. **控制台里的「高保真点击」是不是被关掉了？** 关掉的话点击必然被识破。
3. **是不是旧版本扩展？** 反检测依赖 `debugger` 权限，改了 manifest 之后必须重载扩展本体，
   再刷新页面。
4. **在模拟页确认状态** —— 底部「反检测」应显示「未检出合成事件」。显示「检出合成事件 N 次」
   就是 CDP 通道没工作，去 `chrome://extensions` 看有没有报错。
5. **倍速是不是越界了？** 上限 1.8，扩展会强制收口；但如果在控制台手动改过
   `video.playbackRate`，守卫要等下一次心跳（2 秒）才会压回来。

> **调试期的一个陷阱**：如果在浏览器自动化工具（比如 BrowserSkill）打开的窗口里测试，
> 那类工具会在页面上注入一层全屏遮挡来接住鼠标事件，CDP 点击会被它整个吃掉 ——
> 表现为「反检测是绿的、落点坐标也对，但元素就是点不中」（诊断行会显示落点命中了
> `BROWSER-SKILL-OVER` 之类的遮挡元素）。换到自己平时用的窗口测就正常了。

### 反检测是绿的，但选项就是点不中

同上一条的最后一句话：先确认不是被别的覆盖层接住了。在页面上点一下选项，
看它的选中态能不能正常切换 —— 如果能，说明页面本身没问题，问题在点击上；
如果连手点都没反应，那是页面结构变了，需要更新选择器（见下一条）。

### 网页 AI 不生效 / 每题都慢十几秒

先点控制台的 **「AI 链路诊断」**，它会一次性摊开这三件事：

1. **站点表加载了吗** —— 显示「未加载」说明 service worker 里的 `importScripts` 失败了，
   去 `chrome://extensions` 看扩展有没有报错，重载一次扩展。
2. **有没有开着的 AI 标签页** —— 一个都没有时，扩展会自己新开一个（默认 DeepSeek）。
   开了但没登录、停在登录页，扩展会直接说"需要先登录"并落回枚举。
3. **页面侧通道的统计** —— 「已问 N / 答对 M」；M 一直是 0 而 N 在涨，说明问题在 AI 那一端。

按现象对：

| 日志/现象 | 原因 | 处理 |
| --- | --- | --- |
| `没找到 XX 的输入框（站点可能改版了）` | 站点改了 DOM，候选选择器全都没命中 | 点「试发一条」，它会报出页面上真实的输入区结构，照着更新 `src/shared/web-ai.js` 里那一项的 `input` |
| `字没能进到输入框` | 输入框拿到了但三条塞字路径都没成功 | 同上，看「试发一条」报的输入框结构；确认 `debugger` 权限可用 |
| `问题没发出去（…试了 N 轮，四条路都没生效）` | 站点不认这次提交 | 点「试发一条」：它会报出发送按钮的 `aria-label` / `disabled` / 尺寸，以及焦点在哪。若 `停止按钮可见：是`，说明有个一直亮着的"停止"元素在干扰 |
| `AI 页没有应答：脚本没能挂到 …` | AI 页面开着，但那一页没挂我们的脚本 | **刷新那个 AI 页面**。最常见的原因是扩展重载过而页面没刷 —— 扩展现在会先自动补注入一次，补不上才报这个 |
| 字在输入框里，但发送按钮一直不点亮 | 提示词太长/带空行，某些站点把它当"没输入完" | 提示词已经是极简版（见第三节），若还发生就点「试发一条」把现场发出来 |
| `等待 XX 回复超时` | 模型在慢慢想，或者页面在要你点"继续" | 把「应答等待」调大；或手工在 AI 页里点掉那个弹窗 |
| `AI 没给出可用答案` | 回包里没有「答案：X」那一行 | 看日志后面跟的原始回包；段落格式变了就改 `parseReply` |
| 每次都要等十几秒且从不命中 | 从没登录过任何 AI 站点 | 先在浏览器里登录一次 |
| 某一题第一次很慢、第二次秒过 | 正常的：第一次问、第二次走缓存 | 不用处理 |

**「AI 链路诊断」里每个 AI 标签页都会标出「脚本已注入 / 脚本没挂上」** ——
这一格是这条链路最容易断的地方，先看它比猜快得多。

排障时把「详细」勾上，能看到每次问询的问询内容、命中来源和耗时。

### 扩展卡片上有红色「错误」

**先点扩展卡片上的刷新按钮（↻）** —— 改过 `manifest.json` 或后台脚本之后必须刷新扩展本体。

历史踩坑记录（均已修复，留作参考）：

| 报错 | 原因 |
| --- | --- |
| `Permission 'debugger' cannot be listed as optional` | `debugger` 不能作为可选权限声明，只能放进 `permissions` |
| `Service worker registration failed. Status code: 15` | 后台顶层代码抛异常导致整个 SW 注册失败 |
| `Uncaught TypeError: Cannot read properties of undefined (reading 'onDetach')` | 没有 `debugger` 权限时 `chrome.debugger` 是 `undefined`，顶层直接访问它就炸了 |
| `The AudioContext was not allowed to start` | 页面还没经历过用户手势就启动 AudioContext，被自动播放策略拦下。现在改成等到第一次交互后再启动 |

### 页面没反应 / 控制台没有 `[知到助手]` 日志

1. 确认当前页面域名匹配 —— 只有 `*.zhihuishu.com` 和本地 `127.0.0.1` 会被接管
2. 打开控制台，看有没有红色的 `[知到助手]` 报错
3. 点控制台里的**重注入脚本**按钮（不需要刷新页面）
4. 还不行就**刷新页面**（扩展是页面加载时注入的）

### 检测不到弹题 / 找不到目录

知到不同版本的页面结构差异很大。内置的探测覆盖了 `studyvideoh5` 与 `onlineweb` 两套主要结构，
外加一层基于「兄弟节点同构 + 字母前缀 + 时长文本」的结构启发式。如果还是抓不到，在控制台点**探测弹题**，它会显示当前探测到的题干、选项和题型。
空白说明识别失败，这时可以在 `chrome.storage.local` 里手动指定选择器覆盖自动探测：

```js
// 在知到页面按下 F12，Console 里执行
chrome.storage.local.get('config', (g) => {
  const c = g.config || {};
  c.selDialog = '.你的弹窗选择器';
  c.selOption = '.你的选项选择器';
  c.selSubmit = '.你的提交按钮选择器';
  c.selPlaylistItem = '.你的目录项选择器';
  chrome.storage.local.set({ config: c });
});
```

填好后刷新页面。留空则回落到自动探测。

### 小章节（1.2.1 这种）没被识别到

目录是**树**，不是平表。知到把课程拆成 `1.2 → 1.2.1 / 1.2.2 / 1.2.3` 这种两层结构时，
章节容器和它内部的课时往往命中同一批选择器。早先的实现用「去重」收尾 ——
而去重的语义是"去掉被别的候选包含的那个"，于是**子项全被当成重复项删掉**，
只剩章节标题本身：它没有时长、点了不播，表现就是"小章节识别不到"+ 自动连播走到一半卡死。

现在 [playlist.js](D:/DSH/zhihuishu-auto/src/content/playlist.js) 走 `flattenLeaves()`：
把命中的容器整棵展开成叶子课时，展开时按文档顺序走，父在前子在后，
所以 `next()` 顺着走就行。（顺带修了一个真 bug：结构启发式算了半天分，
`best.items` 一直忘了赋值 —— 那条兜底路径等于从来没生效过。）

判断「容器 vs 课时」用的是**有没有块级的元素子节点**，
不是"内部有没有时长文本"—— 后者会把平表条目里那个 `<span>32s</span>`
当成课时收进来，目录里就多出一堆纯时长条目。

### 排障第一眼：AI 页必须在前台

**先确认 AI 站点那个标签页是当前激活的。** 这一条排在最前面，因为不符合它的时候，
所有症状都长得像"插件坏了"：

| 你看到的 | 其实原因 |
| --- | --- |
| 字进了输入框，但没发出去 | AI 页在后台 |
| 点了发送按钮没反应 | AI 页在后台 |
| 敲回车没反应 | AI 页在后台 |
| 题目前面几道能答，后面突然全都答不出来 | 中途把 AI 页切走了 |

只有**浏览器主页面是 AI 端**时，对 AI 答题的这套改动才会正常运行 ——
知到页可以安心放后台（它有保活），AI 页不行。
具体机制和原因见前面 **「⚠ 前提：需要把浏览器挂在 AI 页面」**。

### 排障第二眼：构建标记

每次启动都会打一行带**构建标记**的日志：

```
[知到助手] 知到自动助手已就绪 · 构建 b85 (2) · 模式=视频 · 自动连播=开 · 自动答题=开 · 题库 0 题
```

控制台页脚也显示 `v1.3.0 · b85 (2)`。

**为什么值得专门做一个**：排障时最怕"截图里的日志到底是哪个版本"说不清 ——
旧版本和新版本的行为不一样，猜错方向就白改一轮（这轮返工里就吃过好几次）。
有了它，看一眼就知道浏览器里跑的是不是刚改的那份代码。
改完代码记得把 `defaults.js` 里的 `BUILD_ID` 往后挪一位。

### 日志区怎么读

- **默认跟着最新一行滚**，但只要你往上翻，它就**停下来** ——
  原来的版本每秒轮询一次、每次把 `scrollTop` 顶到底，
  于是想看前几行永远是白费力气。
- 翻上去之后右下角会出现 **「↓ 最新」**，点一下回到实时跟随；
  自己滚回底部也会自动恢复跟随。
- 保留的是**离底部多少像素**，所以日志继续变长时，你读到的还是同一段。
- 内容没变就不动 DOM，也就不会每秒打断你的阅读。

### 答题时视频卡住不动

弹题弹出时扩展会主动「抱住」播放控制权，避免自己的保活逻辑把视频抢播起来。
如果弹窗因为异常一直不关，扩展会在 8 秒后释放控制权并重试。

### 插件整个不动了（弹窗挂着、视频不走）

这是**闸门没放开**的典型症状。系统里有两道"同一时刻只做一件事"的闸门，
它们本来都在 `finally` 里复位 —— 但如果某个 `await` 因为页面导航、
标签页被冻结之类的原因**永不 settle**，闸门就再也不会打开。现在两道都有自愈：

| 闸门 | 上限 | 到点之后 |
| --- | --- | --- |
| `QuizSolver.solving` | 180s | 强制放闸，日志里记一条 warn，状态机重新捡起这道题 |
| 后台 `aiState.busy` | 180s | 强制放闸（service worker 在等回包的路上被 Chrome 回收时，这个标志尤其容易留下来）|

真遇到的话，日志里会出现 `上一次解题卡了 Ns，强制放闸重新开始`
或 `AI 忙标志卡了 Ns，强制放闸`。

每个 `content` 模块都挂在 `window.__ZHS` 命名空间下，按 manifest 里的数组顺序加载，
不使用打包器 —— 想改哪里直接改，刷新页面就生效。

> `src/shared/defaults.js` 排在最前面加载，所以由它负责创建 `window.__ZHS`；
> 普通页面（popup）侧用 `window.ZHS_*` 那套出口。

`src/shared/web-ai.js` 是唯一被三个上下文共用的文件：content script 与 popup 当普通脚本加载，
service worker 用 `importScripts('../shared/web-ai.js')` 同步加载。
它只放纯函数（站点表、提示词、答案解析），碰 DOM 的部分全在 `src/ai/web-ai.js` ——
这样「问什么」和「怎么读回包」这两件最容易出错的事可以离线断言。

- 第二次遇到同一题时**直接命中题库**，且题库没有重复条目
- `ZHS_QUERY` / `ZHS_ACTION` 通信协议完整
- 重复注入时旧实例被顶掉，消息监听器不累积
- 网页 AI 那一级的出站报文带齐题干、选项、题型与超时；AI 不可用时老实返回 false

`tests/ai-tier.test.js` 把 background 与 AI 标签页整个换成一个假的 `aiBridge.ask`，
于是它验证的是**解题器自己**的行为：什么情况下信 AI（答对就落库、不再枚举）、
什么情况下不信（上一轮 AI 给的组合已经试过就不再问、AI 失败后退回枚举、
开关关掉后一次都不问），以及**优先度** —— 靠给 `aiBridge.ask` 和 `bank.lookup`
一起埋点、把调用顺序记下来，断言「AI 优先」时 AI 排在题库前面、关掉后反过来。

`tests/popup.test.js` 单独管控制台。popup 是唯一"点了没反应也不会报错"的地方 ——
`bindControls` 里那句 `if (!el) continue;` 会把 id 拼错、控件漏加、开关和配置键对不上
全都安静地吞掉。所以在 jsdom 里把它整份跑一遍，断言标签渲染出来了、
开关真的写进了 `config`、按钮真的发对了消息。

`tests/playlist.test.js` 管目录识别。这一类错（嵌套小章节被当重复项删掉）
在真实页面上只表现为"少了几集"，不会报任何错，事后极难定位 ——
所以拿几种典型结构（两层、三层、平表、时长藏在子元素里）各钉一条断言。

`tests/quiz-detect.test.js` 管探测的**防误判**。这个文件里钉住的是两类真实样本：

**不能认的**（认了就会把无关文本发给公网 AI）：

| 样本 | 为什么像题目 |
| --- | --- |
| `第一章: Philosophy`、`1.2.3 Benevolence in the Modern World` | 章节标题，长度和形态都像题干 |
| `以下所有内容均由AI生成请注意甄别` | **站点自己的提示语** —— 带「以下」这个像疑问词的词，长度又正好落在陈述句区间 |
| `Chapter 5: Art: Painting and the Long History of Western Aesthetics` | 长标题是个短语，没有句末标点 |

**必须认的**：

| 样本 | 为什么以前会漏 |
| --- | --- |
| `以下哪个是 HTTP 协议的默认端口？` | — |
| `TCP 是面向连接的传输层协议。` | 没有问号也没有疑问词，靠陈述句兜底 |
| `The unparalleled use of "images" in Chinese classic poetry has exerted deep impacts on Imagism. ( )` | **英语判断题超过 40 个字符**，而陈述句兜底的长度上限就是 40 —— 于是这道题永远检测不到 |

最后那条的修法是给英文加了一条独立分支：**必须是一句完整的话**（结尾有句末标点或答题括号）、
至少 4 个英文词、不像标题、长度放宽到 300。
只放宽长度会把长标题也收进来，所以"是不是一句完整的话"这个判据不能省。

`tests/ai-send.test.js` 单独盯"提交"这一步。它是这条链路最脆的一环，
而"试一遍就放弃"的表现是**插件看着像卡死**（弹窗挂着、视频被 hold）。
这个文件不搭真 DOM，用手写的假对象直接把 `submit()` 驱动起来，
断言：一直失败时会**反复重试**（实测能转到 11 轮）、被独立时限兜住不会无限转、
按钮无效时回车那条路能救回来、输入框本来就是空的时候不浪费时间空敲。

三处刻意的设计：

- **e2e 里会显式关掉高保真点击** —— jsdom 没有 `chrome.debugger`，开着的话点击会发进虚空。
  真实浏览器里的 CDP 链路靠模拟页的「反检测」指标确认。
- **`tests/chrome-mock.js` 还原了一个容易踩的细节**：真实的 `chrome.storage.local.set`
  只会为**真正变化的 key** 触发 `onChanged`。如果 mock 不做这个区分，别的模块写 storage 时的
  空变更会把配置反复刷回默认值，测试就会得到现实中不存在的失败。
- **`ai-tier.test.js` 在做定点断言前会主动 `destroy()` 主实例**。原因是知到答对后弹窗还会在
  页面上停 1.6 秒展示「回答正确」，主循环这期间仍能 detect 到它并再解一次同一道题；
  那些"回声"会混进计数，让断言测到的不是被测代码的行为。

### 改完代码怎么生效

| 改动 | 生效方式 |
| --- | --- |
| content script | 刷新页面（或点控制台的「重注入脚本」） |
| popup | 关掉重开控制台 |
| background / manifest / 新增文件 | 点控制台的「重载扩展」，或 `chrome://extensions` 上点刷新 |
| 配置默认值 | 改 `src/shared/defaults.js`，两边共用 |
| AI 站点选择器 | 改 `src/shared/web-ai.js`，重载扩展 + 刷新 AI 站点页面 |

## 十、已知限制

- **CDP 点击有可见代价**。顶部常驻调试提示条、期间不能用 DevTools。这是绕过 `isTrusted`
  检测的必然成本 —— JS 层做不到这件事。
- **目录结构强依赖自动探测**。知到改版后可能需要更新 `playlist.js` 里的 `ITEM_SELECTORS`
  或 `quiz.js` 里的 `DIALOG_SELECTORS` / `OPTION_SELECTORS`。这是所有页面自动化脚本的共同弱点。
- **组合枚举有代价**。多选题如果有 5 个选项、答案有 3 个，最坏情况要试 26 次。
  大部分平台答错后会把视频回退一段重播，所以枚举会明显拖慢进度。
  网页 AI 那一级就是为了压掉这段代价 —— 但它自己也要十几秒，而且是概率性的。
- **网页 AI 的三个硬前提**：① 你得先在浏览器里登录过至少一个 AI 站点；
  ② 免费版有速率限制，连问几次可能会排队或被要求验证；③ 站点改版会让选择器失效，
  表现为日志里的「没找到输入框」，需要更新 `src/shared/web-ai.js` 里对应项的选择器。
  另外**它是按文本读答案的**，所以只会认「答案：A」这类明确格式；
  模型撒泼写一大段散文时扩展会放弃，落回枚举。
- **AI 站点如果只在 iframe 里渲染对话**，驱动脚本注入不到那一层（`all_frames: false`），
  会表现为「没找到输入框」。目前这几个站点都是主框架渲染，不涉及。
- **Chrome 自带的「询问 Gemini」侧边栏碰不到**。那是浏览器的 UI，不是网页，
  content script 注入不进去。要用 Gemini 就开 `gemini.google.com` 的普通标签页。
- **缓存会存题干**。`chrome.storage.local.aiCache` 里保存着「题目哈希 → 答案」，
  用来给同一道题第二次出现提速；题干本身只截前 200 字存在题库里，AI 缓存只存哈希与下标。
  不需要可以在控制台点「清空 AI 缓存」，或把「同一道题复用上次问到的答案」关掉。
- **判定依赖平台的反馈形式**。如果某个版本的平台既不移除弹窗、又不给任何文字反馈、
  也不换题，扩展只能等到超时然后继续试下一个组合，效率会下降。
- **反检测是军备竞赛**。当前方案针对的是已确认的两处判定。平台若新增检测面
  （例如鼠标轨迹分析、CDP 痕迹探测、行为节奏分析），需要重新分析后应对。
- **不做任何 `currentTime` 拖拽**。很多平台监听 `seeking` 事件来判断异常学习行为，
  直接跳进度是明显的作弊信号。所有操作都走正常的「播放 → 播完 → 切集」路径。
- **音视频保活用的是 40Hz 极低增益振荡器**。它低于绝大多数扬声器/耳机的低频下限，
  正常听不到；但如果你用专业设备或频谱软件，能测到它。不需要可以在控制台关掉「后台保活」。
